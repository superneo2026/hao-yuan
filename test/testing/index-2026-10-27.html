一、公平评测方法：只比较 Harness，不比较模型

同一模型、同一提示词、同一种子仓库、同一隐藏测试、同一预算；三工具都以自动批准模式运行，运行结束后再注入隐藏测试。

1.1 统一条件

  • 模型：三者统一 mimo-v2.6-flash。豪源走内置 MiMo provider（本次评测前修复了缺失的 provider 注册）；Claude Code 走 MiMo 的 Anthropic 兼容端点；OpenCode 走 OpenAI 兼容 provider。
  • 任务：同一份中文提示词、同一份种子仓库、同一套可见测试；每次运行复制到独立目录并初始化 git 基线。
  • 权限：豪源 gate_mode=allow_all；Claude Code --dangerously-skip-permissions；OpenCode --auto。
  • 预算：基础题 900s，困难/长程题 1200s；超出记为超时。豪源单次模型调用 150s 上限、失败重试一次，并禁止跨模型回退。
  • 验收：运行后注入 tests_hidden，执行 pytest tests tests_hidden；运行前后对 tests/ 与 pyproject.toml 做 SHA-256，任何改动直接 0 分。

1.2 防作弊与可复现

  • 隐藏测试不在种子仓库中，模型无法提前读取或针对性修改。
  • 受保护文件哈希不一致 → 该任务 0 分（本次三工具均无违规）。
  • 记录每次运行的 tool 调用、token、耗时、改动文件、验证命令；原始 JSON 与 pytest 日志全部落盘。
  • official-r1 使用交错顺序（同一任务依次跑三工具），降低时段/延迟偏差。

1.3 评分口径

  • 产品加权（主榜）：0.65 正确率 + 0.15 速度 + 0.10 成本 + 0.10 工程纪律。
  • 等权口径（对照）：0.40 正确率 + 0.20 速度 + 0.20 成本 + 0.20 工程纪律。
  • 速度：每题以三工具最快者为 100 归一化，再按任务权重加权；长程题权重更高。
  • 成本：按 MiMo 名义价 2 元/百万输入、8 元/百万输出折算；同价下只比较 token。
  • 工程纪律：完整性哈希通过且至少执行一次测试/构建命令。

六、自适应强度与长程任务：简单题不铺张，长程题能收口

简单题（t1）

豪源 64s / 11 调用；Claude 75s / 11；OpenCode 96s / 15。豪源未使用子代理，工具集自动裁剪为 lite 模式，验证一次即结束。

豪源路由：level=normal/simple → lite=true 可用工具：read_file, read_range, search_symbol, apply_patch, edit_file, write_file, grep, glob, list_dir, run_shell → 不启动 plan/subagent，不加载全量 repo map

长程题（d4）

d4 需要跨 8 个文件实现游标分页与过滤 DSL，并更新 docs；豪源在 470s 内完成 48 次工具调用并通过 75/75 隐藏测试。关键不是“多给提示”，而是提前装配相关源码、减少重复探索。

复杂题上下文装配： 1) 按需求检索排序 top 文件（repoindex.rank_files） 2) 预装 ~30KB 相关源码 + README/docs（context_pack） 3) 保留 repo map 作为符号索引 4) 编辑后只读目标区间，避免重复整读
自适应结论：豪源在 t1（简单）与 d4（长程）之间切换了不同策略：简单题裁剪工具集、跳过计划；复杂题预装上下文、保留计划与验证闭环。这正是本次要考察的“按问题复杂度自适应”，而不是所有题都用同一套重流程。
七、自迭代记录：从“能跑”到“能赢”的真实修复

先用豪源试点，发现缺陷就改代码再复跑；以下只列有数据支撑的改动，并包含一次被证伪的旧结论。

① 修复 MiMo provider 缺失 关键修复

初期发现豪源的 resolve("mimo", ...) 会回退到 deepseek，导致“MiMo 评测”名不副实。新增 mimo provider、严格 provider 模式（禁止跨模型回退）并在网关层校验；修复后所有运行均为 mimo-v2.6-flash。

② 需求感知的 repo map 保留

repo map 之前只按目录/符号字母序输出。改为先按用户需求对文件排序，在顶部给出“最相关文件”，再给全量符号索引；定位题减少无效读取。

③ 相关源码预装（context pack） 保留

对复杂编码题，预装按需求排序的 30KB 相关源码与 docs，并明确告知“已预装、不要重复整读”。d4 从 1200s 超时降到 470s，调用数从 82 降到 48。

④ 进程树回收 保留

模型自写的并发验证脚本可能死锁；旧实现只杀 shell，留下孤儿 python 进程拖慢后续任务。改为 CREATE_NEW_PROCESS_GROUP + taskkill /T，超时后回收整棵进程树。

⑤ 单次调用上限与同模型重试 保留

一次模型调用卡住会吃掉整个任务预算。bench 环境将单次调用上限降到 150s，失败后同模型重试一次，再失败才报错；避免长尾拖垮分任务计时。

⑥ 简单题效率提示 保留

系统规则加入“单符号修复不建计划、不扫全仓；编辑后最多验证两次；通过即停”。t1 从此前 93s/多次探索降到 64s。

负结果也保留：早期一次“对所有困难题都开启强审计”的尝试让 d4/d6 变慢 2-3 倍，已回滚。结论是：对强模型，harness 的胜负手是“少做无用功 + 及时收口”，不是“加更多提示”。
八、局限、复现与证据

必须说明的局限

  • 正式对照每个任务 1 轮；d4/d6 使用冻结代码后的独立复跑批次（豪源 d6 在 official-r1 另有 330.9s 复跑，同样 100%，本报告采用同批次 221.6s）。仍不足以消除模型随机性与网络抖动，建议生产评测再补 2-3 轮。
  • 只评测一个模型（mimo-v2.6-flash）。换模型后排序可能变化。模型延迟方差明显：Claude 的 d3 在先前批次为 623s、本次 official-r1 为 884s；报告采用 official-r1 交错数据。
  • 成本为统一名义价折算，未计缓存折扣与网络波动；token 统计口径三者略有差异。
  • 任务由本报告作者设计，不能替代 SWE-bench 等公开基准；隐藏测试 + 防篡改 + 多工具同条件降低了“只改测试”和“碰运气”的空间。
  • d5 规格考古题三工具都只差同一个时间区隐藏用例（98.4），区分度不足，未纳入主榜。

一句话总结：在同一个 mimo-v2.6-flash 下，三个 harness 的正确率都到 100%；豪源通过“MiMo 正确接入 + 需求感知检索 + 复杂题上下文预装 + 进程树回收 + 简单题轻量路由”，在长程/性能题和 token 成本上建立优势，产品加权与等权口径均为第一。OpenCode 与 Claude Code 各自在个别任务上更快，但综合效率与成本落后。
