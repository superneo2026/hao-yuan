一、公平评测方法：把“模型能力”和“Harness 能力”拆开

评测只比较 Harness。模型统一为 deepseek-flash，任务提示词完全一致，工作区从同一份种子仓库复制，验收测试在运行结束后再注入。

1.1 统一条件

  • 模型：三者都使用 deepseek-flash。Claude Code 走 DeepSeek 的 Anthropic 兼容端点（https://api.deepseek.com/anthropic）；OpenCode 走 OpenAI 兼容 provider；豪源走内置 DeepSeek provider。
  • 任务：同一份中文提示词、同一份种子仓库、同一套可见测试。每次运行前复制到独立目录，并初始化 git 基线（三者一致）。
  • 权限：豪源 gate_mode=allow_all；Claude Code --dangerously-skip-permissions；OpenCode --auto。三者都不需要人工点击，保证可自动复现。
  • 预算：基础任务 900s、转账 1200s、困难任务 1500s；超出记为超时。实际绝大多数运行远低于预算。
  • 验收：运行结束后注入隐藏测试，执行 pytest tests tests_hidden；运行前后对 tests/ 与 pyproject.toml 做 SHA-256 哈希，任何修改直接判 0 分并标记完整性失败。

1.2 防作弊与可复现

  • 隐藏测试不在种子仓库中，模型无法提前读取或针对性修改。
  • 受保护文件哈希不一致 → 该任务 0 分（本次三工具均无违规）。
  • 记录每个任务的工具调用、token、耗时、改动文件数、验证命令，结果 JSON 与日志全部落盘。
  • 所有运行使用独立数据库/进程；豪源每个批次使用随机空闲端口，避免串会话。

1.3 评分口径

正确率是硬门槛；速度/成本是 Harness 差异的主要来源。报告同时给出：

  • 产品加权（主榜）：0.70 正确率 + 0.15 典型速度 + 0.05 尾延迟 + 0.10 成本。
  • 等权口径（对照）：0.70 正确率 + 0.10 典型速度 + 0.10 尾延迟 + 0.10 成本。
  • 典型速度：每个任务取 3 轮耗时的中位数，再对 8 个任务取中位数；不受单个超长任务支配。
  • 尾延迟：全部 24 次运行的 P90；衡量最坏情况。
二、任务设计：短时间能区分 Harness 的 8 个难题

任务不是“写个函数”，而是把定位、跨文件修改、验证、上下文治理、并发/迁移规格理解放进同一个自动验收闭环。基础题保证可解，困难题专门压边界。

为什么能区分 Harness

同一模型下，差异主要来自：能否快速定位、是否只改必要文件、是否主动跑测试、上下文是否被大文件淹没、是否在失败后换策略。

困难题的设计

H1 用 16 线程并发 + 崩溃尾行；H2 用“缺失可选字段/未知字段保留”制造后向兼容陷阱；H3 用假时钟/假 transport 把重试与熔断变成确定性状态机。

反“只改测试”

隐藏测试在运行后注入；受保护文件哈希不一致直接 0 分。因此“让可见测试变绿”不等于通过。

成本口径

统一按 DeepSeek 价格折算：输入 2 元 / 百万 tokens，输出 8 元 / 百万 tokens。Claude Code 的系统提示与工具 schema 更大，单任务输入 token 约 22.8 万，是 OpenCode 的 1.6 倍、豪源的 1.55 倍；因此成本最高。

稳定性

三工具都没有修改受保护文件，完整性 100%。但耗时方差明显：Claude/OpenCode 在 H3 出现过 300s+ 单次；豪源在 H2/H3 也有长尾。困难任务的“模型自测策略”仍是主要方差源。

六、自迭代记录：从“能跑”到“能赢”的 6 次真实修复

整个评测不是一次性跑分。先用豪源试点，发现缺陷就改代码，再复跑；以下只列有数据支撑的改动，包含一次被回滚的负优化。

① Windows 管道适配 保留

试点发现模型执行 pytest ... | tail -40，Windows cmd 下 tail 不存在，浪费一步并污染错误信息。新增 normalize_shell_command：把 | tail -N / | head -N 自动改写为 PowerShell Select-Object，cat 改写为 type；输出中标注 [windows shell adapter]。API 单测覆盖。

② 空回复 / 未写入保护 保留

试点出现一次“读了 7 个文件、没改任何文件就结束”，隐藏测试 18/26、耗时 45s。新增两道一次性 nudge：空回复必须继续；需要代码改动但 0 写入时，强制实现并验证。

③ 版本迁移验收审计 保留（已收窄）

H2 曾出现 25/26：v2 的可选 config 字段缺失时被校验拒绝。加入只读验收审计后，最终 3 轮均为 26/26。最初对所有困难任务开启，导致 H1/H3 变慢 2-3 倍，随后收窄为仅“版本化迁移”任务。

④ git diff 审计 保留

从“子代理读文件”降级为“单次 LLM 读取 git diff + 需求”的轻量审查；同时覆盖已 commit 的改动与未跟踪新文件，避免 agent 自己 commit 后审计看不到 diff。

⑤ 完成态顺序修复 保留

原实现先写 session.status=done 再 finish_run，导致轮询端看到 done 时 step_count 仍为 0。改为先落 run 结果、再置 done，评测可稳定采集步数。

⑥ 过度自测提示词 已回滚

尝试加“禁止新建测试 + 迁移必须测缺失字段”的系统规则，结果 H2 单次飙到 800s、H3 出现 3/18 失败。判定为负优化并回滚，保留原有“跑一次验证”的克制策略。

迭代结论：对强模型来说，Harness 的胜负手不是“多给提示”，而是少做无用功：精准定位、最小 patch、一次验证、失败后换策略。豪源的速度优势来自工程闭环；慢任务则来自审计/自测带来的额外回合，这也是后续优化重点。
七、局限、复现与证据

必须说明的局限

  • 只评测了一个模型（deepseek-flash）。换模型后排序可能变化，尤其是长上下文与工具调用能力不同的模型。
  • 每个任务 3 轮，仍不足以完全消除模型随机性；H3 的长尾尤其明显。
  • 成本为统一价格折算，未计缓存折扣、网络波动、机器负载；token 统计口径三者略有差异（Claude 含 cache read，OpenCode 含 cache read，豪源用 provider prompt/completion）。
  • “产品加权”是主观权重；报告已给出等权口径，OpenCode 在等权下第一。请按团队优先级选择。
  • 任务由本报告作者设计，不能替代 SWE-bench 等公开基准；但隐藏测试 + 防篡改 + 多轮运行降低了“只改测试”和“碰运气”的空间。

一句话总结：在 deepseek-flash 下，三个 Harness 的编码正确率已经打平；豪源以“典型任务最快 + 完整工程闭环”拿到产品加权第一，OpenCode 以“尾延迟与成本最优”拿到等权第一，Claude Code 的正确率同样满分但 token 成本最高。下一阶段要真正拉开差距，需要更长程、更强干扰、更严格成本约束的任务，而不是继续加提示词。
